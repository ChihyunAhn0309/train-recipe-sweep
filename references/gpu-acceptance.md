# Resolve and verify on the actual GPU before a sweep

Read this in every execute invocation, including execution of a plan authored on a CPU-only machine. A plan author may leave target measurements pending; the executing agent must perform them, repair discovered issues within the authorized scope, and select settings from measurements before long trials. This is a required execution phase, not a disclaimer to append and skip.

## Carry a complete plan across machines

For a plan that must work with only the skill and its document, follow [portable-plan.md](portable-plan.md). Do not depend on this chat, the author's cache, absolute home paths, an unprovided trainer, or unspecified decisions. Include the runnable trainer/controller adapter, configs, pinned download manifest, data audit, probe/profile code, launch/resume/report commands and their source hashes in the document. Known assets may be acquired later through those exact commands. Unknown target measurements remain explicit runtime decisions with bounded candidate choices and acceptance conditions.

An executable plan is not a prevalidated GPU result. Distinguish `portable_plan_complete` from `target_verified` and `launch_ready`. If model/task details needed to implement a trainer are missing, ask or resolve them under delegated discretion; do not deliver an instruction to write the real trainer later as a complete executable plan.

## Target acceptance sequence

Persist `target-readiness.json`: for each top-level check, store `pending/passed/failed` (unused subchecks may be `not_applicable` with a reason), evidence path+hash, timestamp, scope/signature, and reason. A Boolean copied from an earlier report is insufficient. Use a signature covering GPU UUID/model/VRAM, host, interpreter/framework/CUDA/driver, trainer/controller code, weights/tokenizer/data/split/ontology/evaluator hashes, method/rank/targets, precision/backend and shape/batch/layout. Reuse evidence only when relevant signatures still match and allocation availability is checked again.

1. **Observed authorized allocation and environment.** Resolve the actual interpreter, driver/framework, GPU UUIDs, running processes, available VRAM, CPU/RAM/disk, and scheduler lease. A configured SSH alias, an assumed RTX model, or CPU smoke does not verify GPU access. If access is absent, keep this stage pending and finish independent preparation; do not repeatedly attempt passwords or start a CPU substitute and call it GPU verification.
2. **Inputs and evaluation.** Fetch the pinned model/data/GT metadata, hash the exact loader paths, audit head/label semantics, split/group lineage and official evaluator. Complete deterministic joins where identifiers allow them; preserve candidate sets and quantify non-identifiability where they do not. Resolve or explicitly bound material leakage/GT ambiguity under the study protocol. Never choose a convenient source ID or rewrite user splits to make this gate appear clean.
3. **Real target forward/backward and persistence.** Exercise each materially different Full FT/LoRA family with real batches and representative maximum shapes. Verify intended parameter groups/gradients/updates and frozen parameters/buffers. Verify head+adapter+processor export/reload, finite losses, evaluation aggregation and checkpoint resume under matching dtype/backend/RNG/data-stream semantics. Predeclare numerical tolerances by precision; do not silently relax a failed tolerance. Target CUDA/backend failures must be fixed and rechecked here.
4. **Controller recovery and resource admission.** Test actual worker launch, atomic identity claim, complete-result reuse, cooperative stop and crash recovery, checkpoint/metric consistency, failed-attempt retention and persistent resource spending with small trials. Validate physical GPU interval accounting against the scheduler/lease and use bounded timeouts. On a cluster use its transactional registry and leases; a Windows local lock test does not validate POSIX or network filesystem ownership. A local controller is acceptable only for its declared scope and after target tests pass.
5. **Measure useful throughput.** Profile each family after warmup with real training, evaluation and save paths, including variable-shape peaks. Compare a bounded matrix of microbatch/accumulation, worker/prefetch/caching, backend/precision when valid, and independent-job packing versus distributed execution when relevant. Preserve effective batch while changing layout where mathematically feasible; changes to precision, normalization, RNG/data order or recipe semantics create distinct identities and require numerical validation. Measure combined peaks and completed work before enabling multiple jobs on one GPU. Do not infer packed throughput from isolated peaks.
6. **Choose and admit.** Choose the stable layout with best useful samples/tokens or completed trials per allocated GPU-hour, with measured memory headroom. Record utilization distributions, allocated/reserved/device memory, warmup versus steady state, eval/save/I/O cost, and measurement variability. Do not maximize a VRAM number with dummy allocations. Estimate anchors/baselines, all requested ranks, failures and confirmation within the remaining budget. Reduce optional coverage transparently if needed; do not silently remove a requested method or invent feasibility. A GPU fit/throughput change can require revised batch/LR/schedule families and new anchors.

All six top-level checks must pass for the proposed GPU launch scope. Only genuinely unused subchecks (for example DDP when no distributed layout is used) may be marked inapplicable with a specific reason. Lack of GPU access is pending, never inapplicable. A missing required measurement blocks the long sweep, not unrelated preparation. Start the minimum-LR registered anchor(s), then the admitted search; observing saturation remains an experiment outcome, not a prerequisite one can infer from GPU profiling.

When using the bundled [study controller](study-controller.md), generate its scope-bound `target_acceptance` manifest from these checks. GPU dispatch refuses missing, stale or corrupt evidence and requires all six gates passed. The controller verifies declared evidence integrity; the executing agent and real target probes establish whether it is true and still applicable. Keep measurements and software schema checks distinct.

Avoid a circular prerequisite for the first controlled GPU test. The plan must implement a bounded integration-probe study before the long-study scope. First run controller ownership/recovery tests with CPU protocol fixtures on the actual host, exercise the real worker directly on the allocated GPU, and gather the standalone smoke/profile/budget evidence. Those component checks can admit only the explicitly bounded probe scope; they do not certify the long sweep. Run that small probe through the controller, verify actual GPU selection, interruption/resume and allocation telemetry, and then include its evidence in a new acceptance manifest for the long study. Never fabricate a passed GPU integration test to bootstrap itself or disable the gate. Give the probe a finite reserved budget and separate diagnostic identity, retain its artifacts, and deduct its cost before admitting the main sweep. This probe is a persistence/resource diagnostic, not duplicate saturation calibration.

## Runtime decisions and revalidation

Continue to sample telemetry during real trials. If the real shape distribution, optimizer/save peak or packed workload exceeds the accepted profile, pause new admissions, preserve running state, diagnose and reprofile. Bound OOM/layout retries; do not change input resolution or effective batch silently. Recheck dependent gates after a change, preserving passed evidence that is still applicable.

Report a pending check as pending until its evidence exists. If the user explicitly defers GPU access, retain this sequence in the plan and skill; do not schedule an automation or attempt remote execution later without a new invocation. When invoked later with authorized access, execute this sequence autonomously without asking the user to repeat previously supplied choices. Only missing consequential inputs, unavailable access or a genuine budget/scope increase require clarification.
