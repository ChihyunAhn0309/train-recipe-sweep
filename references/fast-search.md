# Opt-in fast recipe search

Read when the user asks for a quick search, minimum turnaround, one seed, successive halving, or a tight tuning deadline. Set `search_mode=fast`; preserve `plan` versus `execute` separately. The standard mode remains the default. A fast request authorizes reduced confirmation, not skipping source recovery, GT/split checks, head/LoRA correctness or GPU acceptance. Optimize time to a usable validated checkpoint within a finite budget; neither minimum possible time nor global optimality is knowable in advance.

## Choose the smallest useful search

Record both a **wall-clock deadline** and an aggregate **GPU-hour cap**, allocated devices, methods, acceptable quality loss if supplied, and finish/checkpoint reserve. A GPU-hour ceiling alone is not a turnaround promise. Ask for consequential missing execution limits unless delegated. For delegated fast budgets with no project default, propose an initial ceiling of 2 wall-clock hours and 2 aggregate GPU-hours across the entire study, including setup/profiling/anchors; these are ceilings, not requirements to spend that much. Profile first and reduce the number of candidates/rungs if necessary. Report infeasibility instead of silently dropping a requested rank or raising the budget.

Start with one fixed, prespecified exploration seed per method; pair initialization/data-order streams where meaningful. Fresh multi-seed confirmation is optional in this mode. Do not require the standard three-seed intent before delivering a fast result. Label it `best_observed_single_seed`, `fresh_seed_confirmation_complete=false`, with seed uncertainty unmeasured. If time permits, spend a separately reserved increment on fresh paired baseline/finalist seeds; never mix exploration's winning seed into that aggregate. An explicit later rigorous-validation request returns to the scientific validation contract.

| Situation | Preferred approach | Important boundary |
|---|---|---|
| Only a few runs fit or setup dominates | Source-derived baseline plus a small evidence-led shortlist; full useful exposure | Halving overhead can cost more than it saves. |
| One/few workers, comparable curves | Synchronous successive halving, often 2–3 rungs, retain roughly top 1/2–1/3 | Use the bundled decision helper with a tested trainer/scheduler adapter. |
| Many workers or uneven runtimes | Framework ASHA with measured grace and concurrency limits | Supply a pinned, tested integration; the bundled helper is synchronous, not ASHA. |
| Early ranking is unreliable and budget permits | Longer grace, a conservative bracket or several Hyperband brackets | Extra brackets consume time; do not call one halving bracket full Hyperband. |
| Many coupled axes | Conditional random/space-filling shortlist; optional TPE/BOHB after enough observations | Narrow unsupported axes first; do not fit a surrogate to a handful of noisy points and claim certainty. |

Always include a viable source-derived/proposed baseline. Start near source-supported LR/group ratios and search the most consequential uncertainties first. Prefer fewer well-founded candidates to an uninformative Cartesian grid. Keep the source-to-target ledger: an omitted on/off comparison (including multi-scale) must be explicitly fixed/deferred with rationale, and cannot be claimed completed. A cheap data/resolution proxy can screen only after evidence of useful ranking agreement; it defines a different fidelity/cohort. Final selection must use the requested data, transforms and full validation evaluator. Never merge scores across subsets, resolutions, ranks or inconsistent evaluators.

## Calibration and protection from premature pruning

Start the minimum-positive-LR anchor in each required convergence family first, with its own registered config and reusable checkpoint. Protect it from competitive pruning. Fast mode may predeclare a bounded anchor allowance and censored fallback: if actual learning occurs but saturation is not observed in that allowance, retain the run and continue a fixed-horizon diagnostic search with `saturation_calibration_complete=false`. A time cap is not an observed saturation epoch. Stalled/nonlearning anchors require diagnosis or a declared LR-bound revision, not a fabricated horizon. Do not automatically spend the whole fast budget waiting for an arbitrarily tiny LR.

Use an observed anchor horizon when available; otherwise choose a conservative source-derived/proposed immutable horizon and disclose its uncertainty. Budgeted continuation of the same anchor does not repeat its prefix. Existing controller anchor gating needs the declared diagnostic fallback when censored; it must not be bypassed by marking a capped anchor saturated. Protect at least the baseline and, when feasible, one prespecified slow/late-learning control through the full horizon. A baseline can share an identical anchor trial, without duplicate training.

Distinguish a standalone calibration run from a protected candidate inside the halving cohort. A standalone anchor can exhaust its declared calibration allowance and remain censored in the overall registry; a separately declared diagnostic cohort can then proceed. An anchor included in the helper cohort is protected through its final rung and must be funded accordingly. If importing an already trained prefix into that cohort, the real adapter must validate identical config/trajectory, account for existing work and reach an exact rung without replay; the helper does not import off-rung state. Never enlarge a short cosine schedule and call it equivalent continuation.

Choose the first competitive rung after warmup, demonstrated learning onset, and sufficient comparable evaluations. Predeclare per-candidate `prune_after_resource` to cover slow LR, delayed unfreezing or other relevant transitions. If late augmentation/LR phases can reverse ranking, use longer grace or a conservative control/bracket and disclose the remaining risk; a heuristic grace period does not eliminate late-winner risk. If protection makes the candidate set unaffordable, reduce its initial size instead of secretly pruning protected runs.

Pruning is resource allocation, not saturation or overfitting. Compare validation at the **same resource rung**, with the same metric/evaluator and cadence. Predeclare whether promotion uses the current rung metric or validation-best-so-far. Prefer best-so-far when the deliverable is the validation-best checkpoint; matching evaluation opportunities matters because maxima favor noisier or more frequently evaluated runs. Current-rung ranking can discard an already better checkpoint; retain that artifact and consider a budgeted rescue. Training accuracy alone is unsuitable. Rungs can be dataset passes, updates, samples or nonpadding tokens; choose an exposure unit that remains comparable when batch size differs. Do not rank by wall time unless time-to-quality is explicitly the objective. Failures, missing results and NaNs are not poor valid scores.

## Rungs, budgets and continuation

A proposed small-cohort example is nine exploratory candidates plus one protected baseline, rungs at `3, 9, 27` equivalent epochs, and unprotected survivors `3, 1`. Without extra ties/guards, incremental training costs are `10*3 + 4*(9-3) + 2*(27-9) = 90` candidate-epochs versus `10*27 = 270`. This is an exposure calculation, not a measured 3× wall-clock speedup; downloads, anchors, validation, save/reload, packing and failures change real time. Rung values and reduction factor are engineering choices, not universal defaults.

Allocate a finishing reserve before exploration—e.g. 25–40% of the available execution allowance as an initial estimate—then replace the estimate with measured remaining cost for the baseline plus top 1–2 candidates, full validation, save/reload and export. Finish may be the final rung itself; do not reserve or charge it twice. Under extremely small budgets, reduce breadth, use two rungs, or run only a shortlist. Stop admitting candidates when their conservative remaining reservation would consume the finish reserve or deadline slack. Retain a verified best-so-far checkpoint even if no candidate reaches final fidelity, and label it provisional.

The LR schedule and full trajectory cap are fixed **before rung 1**. Rungs are pause/review points, not new short schedules. On promotion restore last resumable weights, optimizer, scheduler, scaler, RNG/sampler/data position, cumulative exposure, metrics and best-checkpoint tracking. Resume from the **last** state, not the validation-best weights. Preserve the best checkpoint independently for delivery. Do not restart cosine/linear decay at each rung, reset optimizer, replay completed batches, or count resumed prefixes as independent seeds. New seed/recipe/schedule changes create new trials. Changing data fidelity needs a separately declared trajectory, not fake equivalent continuation.

During execution measure useful throughput and save/eval overhead. Use safe mixed precision, batching/accumulation, loaders, caching and independent packing only after correctness/profile checks. Compilation overhead must be amortized by the expected remaining work. Avoid fixed high-frequency evaluation when it dominates; choose and freeze cadence before selection, and retain enough observations for grace/stopping. Do not change batch semantics just to fill VRAM. ASHA can reduce idle waits but needs sufficient comparators and protections against arrival/straggler bias. Count actual wall time and physical GPU allocations, including preflight and failed work.

## Bundled synchronous decision helper

`scripts/fast_search.py` supplies deterministic ranking/promotion and artifact-integrity checks for **one comparable method/fidelity cohort**. It does not dispatch workers, reserve money/time, prove checkpoint semantics, enforce science against fabricated measurements, or implement ASHA. Use separate plans for Full FT and each LoRA rank and materially incomparable regimes.

Plan fields:

- `schema_version=1`, `method`, one integer `seed`, `comparison_context_sha256`, `metric={name,direction}`, `resource_unit` (`updates`, `samples`, `tokens`, or integer equivalent `epochs`). The comparison-context manifest covers model/data/split/evaluator and fidelity semantics and must be supplied by the adapter.
- Strictly increasing positive integer `rungs`; `keep_counts` has one positive nonincreasing top-k quota per transition; `ranking` is `rung_metric` or `best_so_far`; nonnegative absolute `tie_margin` in metric units.
- `candidates`: each contains the full immutable `config` plus `roles` (`candidate`, `baseline`, `anchor`, `late_control`) and positive `prune_after_resource`. Configs repeat the cohort method/seed/context/metric, declare `max_resource` equal to the last rung, and contain their immutable `schedule`. Include all other identity-defining model/training fields. IDs are canonical UTF-8 JSON SHA-256. Combine roles for identical configs.

An immutable history snapshot contains `plan_sha256` and `observations`. Each observation has `trial_id`, exact rung `resource`, and either `status=failed` with a reason or `status=ok` with finite `metric`, `best_metric`, `best_resource`, and `resume_checkpoint`, `best_checkpoint`, `metrics` references. Each reference is `{path,sha256,bytes}` relative to the artifact root. The resume checkpoint may be a single archive containing all consistent training state; the best checkpoint is independently reloadable. Hashes cannot prove that the actual tensors/optimizer belong to the declared trial: the trainer must embed and validate identity, exposure and evaluator metadata.

The helper waits for the complete active cohort at a rung, selects top-k eligible nonprotected candidates, and additionally retains protected/grace candidates and ties within the declared margin. These extras can exceed the nominal quota; the outer budget gate must admit them or return insufficient-budget status. A failed protected control blocks promotion for repair/revision. Unknown, duplicated, stale, future or pruned-branch observations fail, as does lost/regressing best-checkpoint state. At the final rung it ranks only surviving candidates that actually reached final fidelity, including the baseline, by validation-best metric with config-hash tie-breaking. It also exposes the verified best checkpoint at any fidelity and sets `better_nonfinal_checkpoint_exists` when a candidate absent from the final valid ranking had a better observed checkpoint. Failed and pruned histories remain separate; review the failure cause before using an earlier checkpoint from a failed run. Do not discard a useful artifact or pretend it reached the final horizon; a rescue requires a declared new bracket/policy revision retaining cost and lineage. Completed exposure does not imply saturation.

```sh
python scripts/fast_search.py fast-plan.json
python scripts/fast_search.py fast-plan.json --history history.json --artifact-root run
python tools/run_fast_demo.py --output fast-demo --compare-exhaustive
```

The first command validates the plan and prints its hash/IDs. The second proposes `needs_work` actions with fixed target exposure and prior resumable checkpoint, or a final ranking/pruning log. The adapter must atomically claim actions in its durable registry before launch; repeated calls alone do not deduplicate launched workers. Preserve every observation/decision and cumulative cost. Failed observations require a recorded new policy/history revision and preserved accounting; do not erase attempts to retry.

The demonstration trains a tiny CPU classifier on generated data, pauses/restores it, and optionally compares with exhaustive training in that toy setting. It is not pretrained Full FT/LoRA, target-GPU evidence or a general quality/speed guarantee. Its full-reference work is separate validation overhead, not credited as fast-search savings.

## Executable handoff and final checkpoint

Choose a real model-specific scheduler integration. The existing `study_controller.py` does **not** consume helper actions or offer selective rung pause/promote operations; `study_extend.py` appends new configs and is not same-trial rung continuation. Do not change config horizons or call `run --resume` on every stopped candidate to simulate promotion. Implement/test a selective durable scheduler adapter, or use a pinned framework scheduler with equivalent identity, ownership, budget, checkpoint and GPU-acceptance controls. A specification-only plan may leave that implementation pending; a complete document-only GPU handoff must contain it.

The complete handoff includes mode/limits/seed policy, candidate generator, rungs/grace/protection/ties, calibration fallback, finish reservation, actual trainer and scheduler, atomic checkpoint protocol, dataset/source manifests and GPU gates. Test promotion against uninterrupted continuation, no duplicate prefix training, prune isolation, deadline/budget exhaustion, crash/resume and checkpoint corruption. CPU tests keep `target_gpu_verified=false`.

The adapter's aggregate report must separately link `anchor_evidence` and `saturation_calibration_complete`, `learning_and_grace_verified`, `target_gpu_verified`, `deadline_utc`/actual elapsed time, the cumulative physical GPU ledger, required protected/finish reservations, and `final_fidelity_complete`. Required anchor evidence gates admission to the main search; bounded calibration/probes are allowed to create that evidence. Learning/grace evidence gates competitive pruning/promotion, not the initial training prefix needed to observe learning; retain or diagnose an unready candidate within its allowance. Deadline and affordable protected/finish reservations gate every launch. An explicitly declared learning-but-censored anchor can admit a diagnostic search; it cannot pass saturation calibration. Include probes for successful bounded bootstrap and rejection of absent/stalled main-search anchors, premature pruning, expired deadlines and insufficient finish budget in the generated adapter tests. Helper `status=complete` alone certifies none of these workflow states.

Deliver one recipe/checkpoint per requested method when available, with achieved fidelity, baseline delta, selected/best/stop step, pruning/failure history, actual wall/GPU time, remaining search gaps, calibration state and seed limitation. Full FT exports the model and processor/head/label map. LoRA exports adapter config/weights **and all trained heads/other modules**, with exact base checkpoint/processor revision; verify fresh-process reload reproduces the selected validation result within declared tolerance. A weights-only or adapter-only file missing the new head is not a usable result. Do not automatically spend time retraining a winner whose verified checkpoint is already suitable.

## Primary references

[Hyperband](https://jmlr.org/papers/v18/16-558.html) motivates allocating progressively larger budgets to selected configurations; [ASHA](https://arxiv.org/abs/1810.05934) addresses asynchronous parallel allocation. [Ray's scheduler documentation](https://docs.ray.io/en/latest/tune/api/schedulers.html) documents its ASHA/Hyperband interfaces and implementation differences; pin and test the version actually used. The one-seed policy, protection rules, reserves and example rungs here are proposed engineering choices, not guarantees from those papers.
